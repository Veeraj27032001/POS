# POS Application — step3: Master Data

Companion to **step1.md** (technical base) and **step2.md** (Next.js setup). This document defines the master/reference data entities — the "nouns" of the system. Transactions (sales, returns, stock movements — the "verbs") come in **step4.md**.

Every master listed here inherits, by default:
- **BASE-SEC-01** — client only ever sees an opaque ID, never the raw DB key.
- **BASE-SEC-03** — every create/update/delete is audit-logged.
- **BASE-DTR** — every master's list screen uses the count-first, paginated, skeleton-loading pattern.
- Soft-delete (`is_active` flag) rather than hard delete, so history and reports stay intact.

---

## 1. Product — MST-PRD

**Purpose:** the sellable catalog. Each product is a complete, standalone record — "Maggi 10rs Pack" and "Maggi 20rs Pack" are two separate Product records, not a shared parent with variants underneath.

*(Reversed from an earlier base-Product-plus-Variant design — flattened because splitting them added an extra data-entry step for no real benefit once every pack size gets entered as its own distinct item anyway.)*

| Field | Type | Notes |
|---|---|---|
| id | opaque token | BASE-SEC-01 |
| name | string | the full product name, e.g. "Maggi 10rs Pack" |
| category_id | FK → MST-CAT | |
| tax_code_id | FK → MST-TAX, required | every product must have a tax code assigned (HSN, under India's scheme) — see Section 4 |
| track_expiry | boolean, default false | whether this product is expiry-tracked at all — if false, step4's expiry_date fields don't apply |
| images | CDN URLs | via BASE-FUP chunked upload |
| description | text, nullable | |
| pack_size | decimal, nullable | quantity/weight this product represents, in its UOM |
| uom_id | FK → MST-UOM | |
| sku / barcode | string, unique, nullable | the manufacturer's/original barcode — null where the product doesn't have one (loose goods, local/unbranded items). Scanned at checkout the same as `system_barcode` below, when present |
| system_barcode | string, unique | generated by this system, not the manufacturer — auto-created when the product is saved, guaranteed unique regardless of whether `sku/barcode` exists at all. Covers products with no printed barcode and doubles as a fallback for any product. Shown on the product's details page. |
| price | decimal | overridden by MST-PRICE where applicable |
| stock_tracked | boolean | false for non-inventory items (e.g. a service line) |
| reorder_level | integer, nullable | low-stock threshold; null = no alert configured |
| default_cost_price | decimal, nullable | last/standard purchase cost — the basis for the Inventory Valuation report (step6) and updated automatically whenever a Stock Inward item (step4, Section 1) records a `unit_cost` |
| is_active | boolean | soft delete |

**Relationships:** stock quantity is tracked per Product × Warehouse (defined in step4). A Product optionally links to one or more Suppliers.

**Barcode label printing:** a **Print Label** action on the Product screen — single or bulk (select several products, N copies each) — renders either barcode (`sku/barcode` or `system_barcode`, whichever the label is for) as an actual scannable barcode alongside the product name and price, and sends it through the same print bridge step5 already uses for receipts (step2, NJS-23's Electron `window.hardware.print`) — no separate printing mechanism invented for this.

**Two separate barcode listing pages**, since the two barcode types serve different purposes and audiences:
- **System Barcodes** — every product's `system_barcode`, one list.
- **Product Barcodes** — every product's original `sku/barcode` (skipping products that don't have one).

Each page supports downloading/printing a single row, or all of them at once — same underlying Print Label mechanism above, just bulk-triggered for the whole visible list rather than a manual selection.

## 4. Tax Engine — MST-TAX (Generic Schema, India Scope for Now)

**Purpose:** tax must not be hardcoded to one country's rules. This is a small engine, not a flat rate table, so a new country is *configuration*, not a code change.

**Scope for now:** only the India TaxRegion/TaxScheme (GST) is actually being built and seeded right now — real HSN codes, real CGST/SGST/IGST components. The Region → Scheme → Component → Code structure below stays generic on purpose, so a second country is configuration later rather than a rewrite, but no other country's data, seed set, or UI gets built until that's actually needed.

| Entity | Fields | Purpose |
|---|---|---|
| **TaxRegion** | id, country_code (ISO 3166), name | e.g. India, United Kingdom, United States |
| **TaxScheme** | id, region_id (FK), name, is_active | e.g. "India GST", "UK VAT", "US Sales Tax" — a region can have more than one scheme over time |
| **TaxComponent** | id, scheme_id (FK), name, rate_percent, effective_from, effective_to | individual rate lines — e.g. CGST 9%, SGST 9%, IGST 18%, or a single VAT 20%. Date-ranged so a rate change doesn't rewrite history. |
| **TaxCode** | id, scheme_id (FK), code, description, component_group | the classification a product is assigned — e.g. HSN "8471" for India, or a generic "Standard Rate" class elsewhere. `component_group` says which TaxComponent(s) apply (e.g. CGST+SGST for an intrastate sale, IGST for interstate — the actual component selection at sale time is a step4 transaction rule) |
| **ProductTaxCode** | product_id (FK), tax_code_id (FK) | assigns each product a code; a product sold in multiple regions can have one mapping per scheme |

**How it resolves at the point of sale:** the active Store/Branch (MST-STORE) determines the TaxRegion → active TaxScheme → the product's TaxCode within that scheme → the applicable TaxComponent(s) for that specific transaction (e.g. same-state vs different-state in India). That resolution logic is a step4 transaction rule, not a master — this section only defines the configuration it reads from.

**Tax code management (generic, per scheme — not India-specific):** the Admin → Tax Codes screen manages TaxCode records for whichever TaxScheme is active in a region — it isn't hardcoded to HSN. India's scheme happens to call its codes "HSN"; a UK VAT scheme or US Sales Tax scheme would use its own code/category set entirely, managed through that same screen. The system ships with a default HSN set pre-loaded for the India scheme; adding a new TaxRegion/TaxScheme later (e.g. UK, US) means loading *that* scheme's own default code set the same way — no code change needed to support a new country's standard, only new configuration rows (per Section 4's Region → Scheme → Component → Code structure). Every Product requires one TaxCode assigned (MST-PRD, tax_code_id is required), whichever scheme it belongs to.

## 7. Store / Branch — MST-STORE

**Purpose:** a physical selling location. Distinct from Warehouse — a store is where sales happen; a warehouse is where stock is held. One store commonly has one linked warehouse, but they're modeled separately so a store can draw from a shared/central warehouse if needed.

| Field | Type | Notes |
|---|---|---|
| id | opaque token | |
| name | string | |
| address | string | |
| tax_region_id | FK → MST-TAX TaxRegion | determines which tax scheme applies at this store |
| timezone | string | store-level default for BASE-DTH-02 |
| default_currency | string (ISO 4217) | feeds NJS-21 formatting |
| gstin | string, nullable | the store's GST registration number, printed on tax invoices |
| logo_url | CDN URL, nullable | via BASE-FUP chunked upload; printed on receipts |
| receipt_header_text | text, nullable | e.g. store name/address block above the items |
| receipt_footer_text | text, nullable | e.g. "Thank you for shopping with us" |
| return_policy_text | text, nullable | printed at the bottom of the receipt |
| is_active | boolean | |

**Receipt fidelity — this matters:** the four receipt fields above are live, editable settings — but a printed or reprinted receipt must never read them live. When a sale is recorded (step4), its receipt content (logo, header, footer, return policy — a full copy, not a reference) is snapshotted into that transaction record at the moment of sale. If the store changes its return policy on the 10th, every receipt for a sale made before that change — even reprinted on the 11th or any day after — still shows the policy that was actually in effect when the customer bought the item. The mechanism itself (the transaction record carrying its own copy of this data, not just a store_id foreign key) is a step4 concern, but the rule starts here: these fields are never to be looked up live for anything historical.

**Note:** NJS-25 (step2.md) is now confirmed, not hypothetical — multi-store with store-scoped access is required. Every store-assigned user only ever sees and manages their own store's data (stock, and anything else store-scoped) — enforced through this master, detailed in Sections 11–12 below.

## 11. Users — MST-USER

**Purpose:** staff accounts.

| Field | Type | Notes |
|---|---|---|
| id | opaque token | |
| name | string | |
| email | string, unique | login identifier, per NJS-11 |
| phone | string, nullable | |
| role_id | FK → MST-RBAC Role | |
| store_id | FK → MST-STORE, nullable | null = cross-store access (Admin/Owner-level roles only) |
| mfa_enabled | boolean | BASE-SEC-03 |
| is_active | boolean | deactivation, not deletion, for audit-trail integrity |

**Store scoping:** `store_id` is null only for cross-store roles. Every operational role (Manager, Cashier, etc.) has a required, single store_id, assigned by an Admin when the account is created — a user can't change their own assignment. Once logged in, every data view (stock levels, transactions, reports) is automatically filtered to that store_id; a Cashier at Store A never sees Store B's stock, even for the exact same Product. Admins (store_id = null) aren't stuck with everything blended together either — they get a store selector to switch between one store's individual data and an aggregated all-stores view.

## 12. RBAC — Roles & Role Rights — MST-RBAC

**Purpose:** who can do what. Implements NJS-13's fixed-role-set decision and feeds BASE-RTE's middleware access checks directly.

| Entity | Fields | Notes |
|---|---|---|
| **Role** | id, name, is_active | e.g. Owner, Manager, Cashier |
| **RoleRight** | role_id (FK), module, action, allowed (boolean) | e.g. (Cashier, "discounts", "apply", true), (Cashier, "products", "delete", false) — one row per module × action per role |

**How this reaches the middleware:** BASE-RTE-01's `middleware/rbac.ts` looks up the current user's Role, checks the requested module/action against RoleRight, and blocks with BASE-RTE-03's access-denied message on a `false` or missing row — so adding a new module later only means adding new RoleRight rows, not new middleware code.

**RBAC vs. store scoping — two separate checks, both always applied:** RoleRight governs *what actions* a role can perform (can this role apply a discount? delete a product?). The user's `store_id` (MST-USER) separately governs *which store's data* those actions can touch. RBAC is checked in `middleware/rbac.ts`; store scoping is a `WHERE store_id = current_user.store_id` filter applied automatically wherever store-scoped data is read or written. A Manager role might be *allowed* to edit stock in principle — their own store_id still confines them to their one store unless their account is explicitly cross-store (store_id = null).
